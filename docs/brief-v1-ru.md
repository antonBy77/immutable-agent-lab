# ANTON-LAB: Immutable OS + изолированные харнесы агентов
**Автор:** Hermes ⚕ · 18.09.2026 · Статус: БРИФ ДЛЯ ДЕБАТОВ (v1)
**Инициатор:** Антон. Ноутбук готовится отдельно, это тестовый стенд, не прод.

---

## 1. Суть эксперимента

**Проблема:** все харнесы (Hermes, Gemes, DSH и остальные агенты OpenClaw) живут в одной
ОС рядом с Антоном. Любой агент с правами записи может повредить общее окружение:
конфиги, секреты, рантайм-код. Один сбой — чинят все.

**Идея:** неизменяемая (immutable/atomic) ОС на хосте, каждый агент — в собственной
контейнерной среде. Хост невозможно сломать; среда агента — disposable (пересоздаётся
из образа за минуты).

**Шаг 2 (потом):** оркестратор живёт в VM внутри immutable OS (kernel-level изоляция),
его инструменты и периферия — в контейнерах рядом.

## 2. Выбор immutable-дистрибутива (анализ на берегу)

| Дистр | Механизм | База | Плюсы | Минусы |
|---|---|---|---|---|
| **Fedora Silverblue/Atomic** | rpm-ostree/OSTree | Fedora | Зрелое комьюнити, Toolbx/Distrobox из коробки, podman родной, atomic rollback | Слои пакетов (rpm-ostree install) лучше не злоупотреблять |
| **Vanilla OS 2 Orchid** | ABRoot A/B-разделы | Debian sid | Apx — пакеты любого дистра в контейнерах, концепция «контейнеры как ОС» | Debian sid = rolling-сюрпризы, комьюнити меньше, доки сыреют |
| **openSUSE Aeon/MicroOS** | transactional-update + Btrfs snapshots | Tumbleweed | Снапшоты Snapper, rolling, MicroOS заточен под контейнеры | GNOME-центричный (Aeon), меньше привычных Антону удобств |
| **Bluefin (Universal Blue)** | OSTree поверх Silverblue | Fedora | Из коробки dev-инструменты, cloud-native ф philosophy | Ещё один слой абстракции |

**Рекомендация Hermes:** **Fedora Silverblue или MicroOS** — нативный podman + distrobox,
контейнерная философия на уровне самой ОС. Vanilla OS интереснее концептуально, но
Debian sid база для стенда, где важна предсказуемость — минус. Решение за дебатами.

## 3. Архитектура (шаг 1)

```
┌─────────────────────────────────────────────┐
│  Immutable host (Silverblue/MicroOS)        │
│  root read-only, atomic updates, rollback   │
│                                             │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐    │
│  │ hermes   │ │ gemes    │ │ dsh      │    │
│  │ container│ │ container│ │ container│    │
│  │ podman   │ │ podman   │ │ podman   │    │
│  └──────────┘ └──────────┘ └──────────┘    │
│  ┌──────────────────────────────────────┐   │
│  │ shared_workspace (bind mount, rw)    │   │
│  └──────────────────────────────────────┘   │
└─────────────────────────────────────────────┘
```

Каждый контейнер: свой пользователь, свои ключи, только нужные маунты.
Обмен между агентами — через `shared_workspace` (уже так работаем).

## 4. Что говорят источники (важно!)

- **«Контейнеры — это НЕ песочница безопасности»** (dev.to, 10.01.2026): контейнеры
  делят ядро хоста. Это изоляция процессов, а не security boundary. Для защиты от
  *недоверенного кода* нужны microVM (Firecracker, Kata) или gVisor.
  → Для нашего кейса (свои агенты, trusted, но с ошибками) контейнеров достаточно:
    цель — защита от случайного ущерба, не от злонамеренного побега.
- **Devcontainer-паттерн** (markphelps.me, 19.02.2026): бинд-маунтить только конфиг
  агента (~/.claude, skills), НИКОГДА весь $HOME. Blast radius агента = контейнер.
  Тогда можно включить автономные флаги (--dangerously-skip-permissions) безопасно.
- **Docker Sandboxes** (docs.docker.com): microVM-изоляция «из коробки» — полезный
  референс для шага 2, но диктует свои образы. Свой podman = полный контроль.

## 5. Риски и открытые вопросы (для дебатов)

1. **Сеть:** агентам нужен интернет (web_search, API). Ограничивать ли egress?
   Драфт: разрешить всё на шаге 1, политику — на шаге 2.
2. **Секреты:** API-ключи не бинд-маунтить массово; каждому контейнеру — свой
   минимальный набор. Кто хранит мастер-копию?
3. **Состояние:** персистентность (memory, сессии, Redis, Qdrant) — named volumes
   или отдельные контейнеры-сервисы, общие для всех агентов?
4. **Ресурсы ноута:** 3+ харнеса + LLM-рантайм? CPU-only, ~16GB RAM — квоты cgroups
   обязательны, иначе один агент съест всё.
5. **Торговля:** если в стенд попадает trading-пайплайн — двойное подтверждение
   исполнения, никакой автономии в ордерах со стенда.
6. **Обновления:** atomic rollback ок, но контейнерные образы тоже надо версионировать
   (git + build script), чтобы пересоздание агента было воспроизводимым.

## 6. План (черновой)

| Этап | Что делаем | Ответственный |
|---|---|---|
| 0 | Ноутбук, BIOS, установка host OS | Антон |
| 1 | Дебаты агентов по брифу, фиксация решений | все, финал к 06:10 (формат как 20.08) |
| 2 | Базовый образ агента (Dockerfile): node, python, hermes/gemes/dsh runtime | Hermes + ZCode |
| 3 | Podman compose: 3 контейнера + shared_workspace + общие сервисы (Redis 6380) | Hermes |
| 4 | Перенос конфигов/памяти (только необходимое, не $HOME) | каждый агент |
| 5 | Недельный прогон, журнал инцидентов, выводы | все |
| 6 | Шаг 2: оркестратор в VM (KVM/libvirt) внутри immutable host | ZCode + Hermes |

## 7. Позиция Hermes (неNeutral)

**За.** Схема правильная и зрелая: immutable host убирает целый класс аварий,
контейнер на агента даёт воспроизводимость и честные blast radius. Devcontainer-опыт
показывает: с изоляцией можно спокойно включать автономные режимы.

**Против спешки.** Главная ловушка — маунты. Один «удобный» бинд $HOME обнуляет всю
схему. Правило: маунт только того, что агент умеет пересоздать.

**Спорный момент для дебатов:**MicroOS vs Silverblue; и делать ли общие сервисы
(Redis, Qdrant) хостовыми контейнерами или отдельными подами.
